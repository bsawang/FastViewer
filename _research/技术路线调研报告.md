# FastViewer 技术路线调研报告

**日期**：2026-11-06
**环境**：Windows 10 19045 x64；Chrome **157.0.8103.38**；Edge 浏览器 **146.0.3856.59**；WebView2 Runtime **145.0.3800.97**；CEF stable **156.0.15 / Chromium 156.0.8078.80**
**所有数字均为本机实测**，原始产物在 `_research/webprobe/`（脚本、JSON、截图），逐条对应关系见 §11。

---

## 0. 结论摘要

1. **"本地文件服务 + 浏览器前端" 这条路成立，且是当前最优解**：缩略图墙 45 张冷启 **635 ms**、热 **49 ms**；视频 `<video>` 直接可播，但**必须支持 HTTP Range/206**，否则进度条不可拖（`seekable=[0,0]`）。
2. **零打包（`chrome --app=<url>`）能满足"文件夹浏览 + 界面好看"的大部分**：整个客户区（含右键菜单、浅色/深色、图标、标题文字、尺寸位置）都归页面管；**只有系统标题栏本身动不了**（高度、按钮样式、无边框）。
3. **想彻底去掉系统标题栏**，唯一可行且已实测的路径是：**把站点装成 PWA，再用 `--app-id` 启动**（Window Controls Overlay）。实测 `windowControlsOverlay.visible=true`、页面内容从窗口**第一像素**开始画、自绘栏可拖窗/双击最大化；代价是**首次运行多一步安装**。
4. 运行时不需要换：Edge/Chrome 的图像解码行为**逐项一致（0 项结构性差异）**，WebView2 与 CEF 带来的只是体积和版本号差异，不带来能力差异。**默认不建议**为 FastViewer 引入 Electron/CEF。
5. 参考实现（本机 `web2app`）用的是 **Electron 双层壳**：本地壳页 + `<webview>` 载目标站，能拿到**完全自绘的标题栏与窗口按钮**，代价是 141.3 MB 分发物、Chromium 152。详见 §7。

## 1. 判定基线（需求）

| 项 | 内容 |
|---|---|
| 用途 | 自用 |
| 驱动需求 | ① 文件夹浏览 ② 界面好看 |
| 格式要求 | **低**——"Chrome 能显示的就行"，**不做格式扩展** |
| 视频 | 需要播放（含拖动进度） |
| 不做 | 编辑、格式转换、批量处理 |

由此推出一条判定原则：**凡是"换运行时/换格式库"才能拿到的能力，一律不做；凡是"浏览器本来就有的能力"，一律直接用。**

## 2. 路线对比

| 路线 | 运行时版本 | 磁盘占用（本机实测） | 外观可控度 | 落地代价 |
|---|---|---|---|---|
| **`chrome --app` 零打包** | Chrome 157 | 506.9 MB / 264 文件（系统已装） | 客户区全可控；**标题栏不可控** | 无打包、无安装 |
| **PWA + WCO + `--app-id`** | Chrome 157 | 同上 + 每站点 `Web Applications/` 少量数据 | **连标题栏都可自绘**（右侧系统按钮保留） | 首次需安装一次 |
| WebView2 宿主 | 145（本机已装） | 792.4 MB / 731 文件 | 完全可控（自绘窗口） | 要写宿主程序 |
| Electron | 44.0.0 = Chromium **152.0.7977.54** | zip **141.3 MB** / 解压 **318.7 MB**（本机实测，见 §7.6） | 完全可控（含自绘标题栏） | 要打包、要维护 |
| CEF | 156 | minimal 包 **166.7 MB**（tar.bz2） | 完全可控 | 要写 C++ 宿主，最重 |

**关键判断**：这张表里"可控度"的提升（WebView2/Electron/CEF）换来的只是**标题栏**和跨平台，而标题栏用 WCO 已经能拿到。**能力（图像/视频/解码）三者完全一样**，所以引入打包运行时是净亏损。

## 3. 实测一：图像能力

### 3.1 缩略图墙

夹具：45 个真实文件（含 12MP / 48MP / 108MP / 160MP 大图、渐进式 JPEG、CMYK、动画 GIF/WebP/PNG、多尺寸 ICO、AVIF）。
测法：8 列网格 `<img>` 全量解码两遍，统计 `decode()` 完成时间（`_research/webprobe/gridbig.html`）。

| 轮次 | 张数 | 成功 | 耗时 |
|---|---|---|---|
| 冷（新 profile，无缓存） | 45 | 36 | **635.1 ms** |
| 热（同页二次） | 45 | 36 | **49.3 ms** |

结论：**"缩略图墙"是白送的能力**——显示器尺寸的 `<img>` 会走 DCT 缩放解码，不需要服务端生成缩略图，也不需要专门的 mip 链。热态 45 张 49 ms 意味着滚动时基本无感。

### 3.2 格式边界（这决定"格式需求低"到底低到哪）

- `<img>` 通道：**36/45 成功**。
- `createImageBitmap` 通道：**35/45 成功**（差的一项是 SVG——`<img>` 能画，但 blob SVG 不能进 `createImageBitmap`）。
- **两边都失败的 9 项（Chrome 157 硬边界）**：
  `16bit.tif`、`cmyk.tif`、`rgb.tif`、`rgb16.tif`、`tif_jpeg.tif`、`multipage.tif`（TIFF 全系 6 项）、`sample.jp2`、`sample.qoi`、`probe.heic`。

也就是说：**JPEG / PNG / WebP / GIF / BMP / ICO / AVIF / SVG 全过；TIFF、JPEG2000、QOI、HEIC 不可显示。**
按"不做格式扩展"的既定范围，这 9 项直接列为不支持即可；如果以后想补，补的也是**单个解码器**，不用动架构。

### 3.3 一个实现坑（已踩）

`loading="lazy"` + 容器移出视口（`left:-9999px`）会导致**永不加载**。缩略图墙请用 IntersectionObserver 或保持在视口内的占位，不要依赖 `loading=lazy` 做批量预热。

## 4. 实测二：视频

夹具：`sample.mp4`，640×360，6 s。测法：两套静态服务跑同一页面，唯一变量是**是否支持 Range**。

| 服务 | 首帧就绪 | `buffered` | `seekable` | 硬件解码 |
|---|---|---|---|---|
| **支持 Range（206）** | 206.4 ms | `[0, 6]` | **`[0, 6]`** | `supported / smooth / powerEfficient = true` |
| **不支持 Range（200 全量）** | 49.5 ms | `[0, 6]` | **`[0, 0]`** | 同上 |

**这是整份报告里最硬的一条约束**：不支持 Range 时文件虽然能"播完"，但 `seekable` 恒为 `[0,0]`，进度条拖不动——用户会直接判定"这播放器是坏的"。所以本地文件服务**必须实现 `Accept-Ranges: bytes` + 206 + `Content-Range`**（`_research/webprobe/node-range.mjs` 是可用最小实现）。

`canPlayType('video/mp4; codecs="avc1.42E01E,mp4a.40.2"')` → `probably`；`mediaCapabilities.decodingInfo`（`framerate` 是必填字段，漏了直接 TypeError）报硬件解码可用。

## 5. 实测三：`chrome --app` 的外观与输入可控度

### 5.1 可控 / 不可控

| 想改的 | 能不能 | 怎么改 |
|---|---|---|
| 窗口标题 | ✅ | 页面 `document.title` |
| 任务栏/标题栏图标 | ✅ | `<link rel="icon">`（实测换了图标、标题文字同步） |
| 窗口尺寸 / 初始位置 | ✅ | `--window-size=W,H`、`--window-position=X,Y` |
| 标题栏深浅色 | ✅ | `--force-dark-mode`（整个框变深色，见 §11 截图） |
| 客户区一切（布局、配色、动画） | ✅ | 网页 |
| 页面右键菜单 | ✅ | `contextmenu` + `preventDefault()`，做出来和原生 App 一样（见 `ctx-custom.png` 对照 `ctx-native.png`） |
| 标题栏高度 / 按钮样式 / 无边框 | ❌ | 外部改不了 |
| 标题栏右键菜单 | ❌ | 弹的是 Chrome 自己的（还原/移动/大小/最小化/最大化/重新加载/**打开浏览器窗口**…），见 `ctx-titlebar.png` |
| 系统按钮（最小化/最大化/关闭）外观 | ❌ | — |
| DevTools | ⚠️ | F12 照样打开（自用是加分，交付不行） |

### 5.2 外部改边框 = 死路（已排除）

用 `DwmSetWindowAttribute` 从外部改 Chrome 窗口边框：
- attr **19** 在 19045 直接 `E_INVALIDARG`；
- attr **20** 可以设置成功但**画面无可见变化**；
- attr **33–36**（Win11 22000+ 才有）在该系统不存在。

**结论：别走 DWM 外部改色，深色边框直接用 `--force-dark-mode`。**

### 5.3 测量时的 DPI 坑（记录给后续实现）

PowerShell/宿主进程默认 DPI 不感知，`GetWindowRect` 拿到的是虚拟化坐标（本机第二块屏坐标是负的 `-3217,-1123` 这种），会导致截图错位。**所有窗口测量/截屏前必须先 `SetProcessDPIAware()`**。

## 6. 实测四：PWA + Window Controls Overlay（去标题栏的唯一实测可行路径）

### 6.1 安装链路（不碰鼠标，全程可脚本化）

`manifest.json` 里 `display_override: ["window-controls-overlay","standalone"]`，然后：

1. `http://127.0.0.1` 是 **trustworthy origin**，`isSecureContext=true`，**不需要 https**；
2. Service Worker 注册成功（`sw: "ok"`）；
3. `beforeinstallprompt` 触发（`bip:"fired"`）；
4. 真点击（CDP `Input.dispatchMouseEvent` 的 press/release **都要 `clickCount:1`**）→ `deferred.prompt()`；
5. 返回 `outcome: "accepted"`，profile 下出现 `Default/Web Applications/<app-id>/`，开始菜单出现 `FastViewer WCO Probe.lnk`（参数 `--app-id=<id>`）。

**注意：Chrome 157 没有开放 PWA 相关的 CDP domain**（`/json/protocol` 列出的 59 个 domain 里没有），安装动作必须走页面按钮 + 真手势。

### 6.2 三种启动方式的差别（关键）

| 启动方式 | `display-mode` | `windowControlsOverlay.visible` | `getTitlebarAreaRect()` |
|---|---|---|---|
| `--app=<url>` | standalone | **false** | 0×0 |
| 安装完成瞬间自动弹出的窗口 | standalone | **false** | 0×0 |
| **`--app-id=<id>` 重新启动** | **window-controls-overlay** | **true** | **1054×31 @ 0,0** |

→ **WCO 只在"已安装 + 按 app-id 启动"时生效**。安装完那个自动窗口是 standalone，必须关掉重开。

### 6.3 几何与交互（全部实测）

- 窗口 1300×860 → 客户区 1287×853；**顶部 inset = 0**（真点击 screen(-2825,-735) → 页面收到 `clientX/Y = 294,300`，反推客户区原点 = 窗口左上角），即**没有任何系统标题栏，内容从第一像素开始**（见 `wco-printwindow.png`：页面头部紧贴窗口顶边）。
- `getTitlebarAreaRect() = 1054×31`，右侧 **233 px**（1287−1054）是系统按钮保留区，页面画不进去；`env(titlebar-area-width)` 同步解析为 `1054px`。
- **最大化后变成 1687×26、还原回 1054×31** → 标题栏高度不是常数，**必须监听 `ongeometrychange` 并吃 `env()`**，不能写死。
- **拖窗**：在自绘栏 y=15 处按下拖 (220,120) → 整窗 `movedBy=198,108`，`-webkit-app-region: drag` 生效。
- **命中测试**：往 bar 里注入两个按钮——`region:drag` 的那个**页面收不到点击**（`__D=null`，被框架吃掉用于拖窗）；`region:no-drag` 的那个**正常收到**（`__ND="clicked …"`）。→ **栏内任何可交互控件都必须显式 `-webkit-app-region: no-drag`**。
- **双击 drag 区 = 最大化**（`IsZoomed=True`），符合 Windows 习惯，不用自己实现。

### 6.4 坑清单

1. `getTitleBarOverlay()` 这个名字**不存在**，正确 API 是 **`getTitlebarAreaRect()`**；写错会在 `try` 外抛错，**静默打断整个脚本**（当时表现为 SW 没注册、`beforeinstallprompt` 没监听，看起来像"不可安装"）。
2. app-id 是 **start_url 的纯函数**：两个不同 profile 装同一站点得到同一个 `egeamjhcbjnihimaoedlckopnjjopmjc` —— 启动器可以把 id 写死，不必去读快捷方式。
3. 安装要**真用户手势**；`prompt()` 的 promise 在原生弹窗处理完前一直 pending，别当成失败。
4. WCO 是 Chrome 的能力；**换 Edge/WebView2 需要重新验证**（虽然同引擎，但本报告只在 Chrome 157 上实测过）。

## 7. 参考实现：web2app 的内嵌方案（Electron 双层壳）

> 出处：本机既有项目 `E:\work\ai\web2app`（`src/entry/electron-*.ts` + `electron-toolbar.html`）。以下是**实际代码**的做法与实测数字，不是通用 Electron 教程。

### 7.1 结构：壳页 + guest

`BrowserWindow` 载本地 `toolbar.html`（导航、Tab、窗口按钮全在这一层），内容区放一个 `<webview>` 载第三方站点——**壳 UI 与被承载页面是两个页面**，互不污染。

隔离策略是分层的：

| 层 | webPreferences | 理由 |
|---|---|---|
| 壳页（本地 `toolbar.html`） | `nodeIntegration:true, contextIsolation:false, webviewTag:true` | 本地页，直接给 Node，省掉一层 contextBridge |
| guest（目标站 `<webview>`） | `contextIsolation=yes, nodeIntegration=no, **sandbox=no**` | `sandbox` 必须关：preload 要用 `require('fs')` 读注入包；但**隔离保持开启**，不把 Node 交给第三方站点 |

### 7.2 窗口与标题栏

- `titleBarStyle: 'hidden'` + `autoHideMenuBar: true`，**保留原生窗口边框**：拖拽、贴边吸附、拖边还原、阴影、系统双击最大化全部白拿。
- 标题栏 `#bar { -webkit-app-region: drag }`，按钮/Tab 显式 `no-drag`——**与 §6.3 在 WCO 下测出的命中规则完全一致**，两边是同一套机制。
- **自绘拖拽被废弃过**：跨屏时 `screenX` 会切到另一块屏的坐标系，累加增量会跳；代码里残留的 IPC `shell:drag` 全是补偿（绝对定位 + 位移>120px 视为换屏重锚 + 拖拽期钉死窗口尺寸）。
- **最大化不依赖系统 API**：早期 `frame:false + transparent` 方案下 `isMaximized()` 失真、副屏 `unmaximize()` 是空操作、跨屏 `setBounds` 会存出负几千的坐标；现在改为 `screen.getDisplayMatching(win.getBounds()).workArea` 现算 + `setBounds`，**最大化状态只由窗口的 maximize/unmaximize 事件维护**（系统事件与 DPI 无关，按钮 / Win+↑ / 双击标题栏都能触发）。
- 初始尺寸取工作区 80%、上限 1280×860——写死尺寸在 1440×900 上等于全屏，用户点最大化看不出变化。

### 7.3 注入（如何把脚本塞进被承载页面）

- 在 webview 的 `preload` 里用 **`webFrame.executeJavaScript(bundle)`** 注入到**页面主世界**。关键：preload 默认跑在隔离世界，直接 `eval(bundle)` 只污染隔离世界，页面上看不见效果。
- preload 执行早于页面脚本，等价于 `document-start`；bundle 自己等 DOM 就绪。
- 注入包与内核同目录，路径**一律从 `__dirname` 拼**，不写死 `../dist`——否则远端热更后内核找不到自己的文件。

### 7.4 向 Chrome 对齐的开关（都是踩坑换来的）

| 开关 | 为什么 |
|---|---|
| `--enable-features=OverlayScrollbar` | Chromium 默认那条粗灰滚动条在深色页面上很扎眼 |
| `--autoplay-policy=document-user-activation-required` | 对齐 Chrome 桌面策略；Chromium 默认允许带声音自动播放，广告音频会照响 |
| `app.userAgentFallback = …Chrome/152.0.0.0…Safari/537.36` | Electron 默认 UA 带壳名、结尾缺 `Safari/537.36`，目标站会走**不同的页面变体**（该仓源码注释记录：实测同一页 hero 的 class 都不一样、图片懒加载表现变差） |

### 7.5 网络与分发

- 代理：`session.defaultSession.setProxy()` 应用到默认 session（所有 webview 共用），配置落 `userData`，切换后 reload 所有 webview 立即生效。
- 分发拆成两段解耦：**承载器**（bootstrap + 内置 `kernel-snapshot/`，只有换 Electron 大版本才变）+ **内核**（main / preload / toolbar / inject，热更）。内核下载到 `userData/kernel-<版本>`，用 `kernel-pointer.json` 指版本、`kernel-boot.json` 作"上次成功启动"标记，**标记缺失即回退内置快照**，保证不会白屏。
- 打包：`asar:false`（应用文件以真实目录落在 `resources/app/`，webview 不认 asar 内的 preload 路径），zip 压缩级别 `mx=3`——该仓 `electron-builder.yml` 记录的实测曲线：`mx=1/3 → 141.4 MB`，`mx=7 → 134.2 MB`，但耗时由 7 s 涨到 72 s，收益为负。

### 7.6 体积（本机实测）

| 项 | 数值 |
|---|---|
| Electron 版本 | 44.0.0 → **Chromium 152.0.7977.54**、Node 24.18.1 |
| `win-unpacked/` | **25 个文件 / 318.7 MB** |
| 免安装 zip | **141.3 MB**（148,201,407 B） |

### 7.7 对 FastViewer 的取舍

- **能拿到**：完全自绘的标题栏与窗口按钮（不受 WCO 那 233 px 系统按钮保留区限制）、没有任何浏览器 UI 泄漏（无 F12、"打开浏览器窗口"这类右键项也消失）、可以顺手做多 Tab / 工具栏。
- **代价**：多一份 141 MB 分发物；Electron 44 的 Chromium **152** 比本机 Chrome **157** 落后 5 个版本（能力上已证明 145/157 无差异，但版本落后是持续维护项）；跨屏 DPI 那一串坑必须照抄，否则多屏用户必现。
- **与 §6 的 WCO 对比**：WCO 用零分发的 Chrome 就能拿到"页面自绘标题栏"，但右侧系统按钮区和按钮样式收不回来；**若"界面好看"要卷到标题栏完全自绘、连系统按钮都自己画，Electron 是唯一确定可控的路线。**

## 8. 与 ImageGlass 的对照（为什么换路线值得）

前序对 ImageGlass 源码的审阅（`_research/ig`）结论：它的缩略图走 `MipmapTileCache`，**没有真正的多级 mip 链**，大图缩放靠运行时重采样，所以"缩略图墙 + 流畅缩放"一直是它的弱项。

本方案里：
- 缩略图 = 浏览器 `<img>` 的 DCT 缩放解码（45 张热态 49 ms，**零额外代码**）；
- 缩放/平移 = CSS transform（合成器线程，不重排版）；
- 界面 = 任意 HTML/CSS（"好看"这条需求不再受原生控件限制）。

**代价**：不能显示的文件就是不能显示（§3.2 那 9 项），且没有画质等级的精细控制（插值算法、色彩管理选项）。按当前需求（自用、格式低、好看优先），这个交换是划算的。

## 9. 未验证项与风险

| 项 | 状态 | 说明 |
|---|---|---|
| 任务栏身份（AUMID） | **未验证** | 读 AUMID 时 `hr=0x80004002 (E_NOINTERFACE)`，**不要**把"能固定到任务栏/图标正确"当成已确认 |
| 万级目录 / 滚动性能 | 未测 | 只验证了 45 张；需要做虚拟滚动 + 分页，不能一次渲染全部 |
| 并发解码上限 | 未测 | 160MP 图片单张耗时未单列，建议限制并发解码数 |
| 高 DPI / 多屏混合缩放 | 部分 | 探针踩过 DPI 虚拟化，前端本身未做混合缩放实测 |
| 首次安装步骤的用户体验 | 需设计 | WCO 路线要求首次安装；要么做引导页，要么退化成 `--app` |
| Chrome 升级回归 | 风险 | WCO/`--app` 都是"非承诺 API 面"，Chrome 大版本升级需回归一次 |

---

## 10. 推荐路线

**主线（默认）**：本地文件服务（Node/Python，**必须支持 Range**）+ 前端（缩略图墙 + 灯箱 + 视频）。
启动方式两档，同一套前端代码：

1. **默认档 `chrome --app`**：零安装、零打包，客户区完全自定义，深色边框靠 `--force-dark-mode`。适合"打开就能用"。
2. **精致档 PWA + WCO**：首次安装一次，之后 `--app-id` 启动，**标题栏也由页面绘制**。适合把"界面好看"做到极致。

**默认不做**：Electron / CEF / WebView2 宿主、服务端缩略图生成、mip 链、TIFF/HEIC 解码。其中 Electron 的**具体做法与代价**见 §7——只有"标题栏也必须完全自绘"升级成硬需求时才启用，届时 §7 的代码模式可直接照抄。

分阶段建议：
1. 文件服务（目录列举 + Range + MIME + 缓存头）→ 先跑通视频拖动；
2. 前端骨架（侧栏 + 缩略图墙 + 灯箱），IntersectionObserver 做懒加载；
3. 视觉层（配色、动效、右键菜单、拖拽）；
4. 启动器（`--app` 一键；再做 PWA 安装 + `--app-id` 的精致档）；
5. 回归清单（Chrome 升级、大目录、混合 DPI）。
